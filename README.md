RustPalm 的首版目标是让用户在 HarmonyOS 手机上输入电脑的 RustDesk ID，经过对端授权后看到桌面，用触摸和软键盘操作电脑，并随时断开。建议开发**原生鸿蒙控制端**，界面使用 ArkTS / ArkUI，连接、认证和输入协议复用 RustDesk 的 Rust 会话核心。第一项工程验证是让一台手机控制一台运行官方 RustDesk 的 Windows 电脑。

[开发工具、安装顺序和就绪检查](docs/windows-setup.md)单独列出。本方案及版本依据的核对日期为 2026-11-06。

## 会话如何工作

1. **配置与连接。** 用户配置 ID 服务器地址、受信的服务器公钥以及可选的中继地址，然后输入电脑 ID。电脑先向 `hbbs` 注册，手机经 `hbbs` 找到电脑并尝试打洞直连，失败后经 `hbbr` 转发。界面显示实际使用的路径。服务器公钥来自管理员分发的 `id_ed25519.pub`，电脑访问密码由另一条认证流程处理。[RustDesk 自建服务](https://rustdesk.com/docs/en/self-host/) · [客户端配置](https://rustdesk.com/docs/en/self-host/client-configuration/)
2. **认证与授权。** 通过核心执行 RustDesk 的身份校验、加密握手和对端配置允许的登录方式。公钥错误、密码错误、对端拒绝、只读授权分别显示。公钥不匹配或无法建立加密会话时终止连接。默认只在本次会话内使用密码，日志屏蔽密码、输入内容、帧数据和可识别的设备 ID。[上游会话与握手源码](https://github.com/rustdesk/rustdesk/blob/1.5.1/src/client.rs)
3. **显示桌面。** 从核心取得协商的视频帧，在原生线程解码，交给 ArkUI 的 XComponent 对应的 NativeWindow。第一条可验收路径选 VP8/VP9 软件解码。在实机测得 CPU、延迟或耗电超标后，再评估 H.264 硬解直出 Surface。按设备解码能力和电脑实际编码能力的交集通告格式，解码失败时重新协商到已验证的格式。[移植工程和编解码说明](https://github.com/rustdesk/rustdesk/pull/16779) · [华为解码能力查询](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/obtain-supported-codecs/)
4. **发输入。** 手机将轻点、长按、拖动、双指滚动转换为远端鼠标事件。坐标转换依次扣除黑边、应用当前平移与缩放、换算到对端报告的桌面像素和原点。软键盘分别处理文本提交和实体按键事件，工具栏提供 Ctrl、Alt、Tab 等组合。对端撤销控制权限后立即切换只读，失焦、断开时释放按下的键与鼠标按钮。
5. **结束与恢复。** 用户可在查找、认证和控制期间取消。主动断开或应用销毁时结束会话并释放资源。切后台时释放输入、清空敏感草稿、暂停渲染和连接计时，保留网络会话并申请一次系统短时宽限；前台重绑 Surface 并刷新。系统挂起、回收或网络断开仍可能终止会话，不承诺无限后台保活。新会话独立认证，旧回调不得向新页面送帧或重放输入。

## 模块与边界

| 层 | 职责与实现选择 |
| --- | --- |
| ArkTS / ArkUI | Stage 模型的 UIAbility 管理生命周期。首页负责服务器设置和连接，认证界面接收授权结果，会话页承载桌面、缩放、软键盘和断开操作。首版在应用清单声明联网权限 `ohos.permission.INTERNET`。触摸和软键盘事件由会话页接收并发送给远端电脑。[华为权限说明](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/permissions-for-all/) |
| ArkTS 与原生桥 | 通过 Node-API（N-API）调用 C ABI。接口围绕会话句柄传递连接、取消、认证、输入和状态事件。后台线程经线程安全回调向 UI 报告状态，Surface 单独绑定和解绑，逐帧像素留在原生层。 |
| Rust 核心 | 复用上游连接状态机、打洞／中继、加密认证、协议消息和键鼠映射。按控制端需求裁剪编译特性；保留服务端、电脑端的协议行为。管理会话生命周期，拒绝已销毁句柄的调用。 |
| 原生视频与存储 | 为画面使用有界队列，渲染过期时优先保留可显示的最新帧，保持压缩流的参考帧依赖。Surface 重建后重新绑定解码器。服务器配置存在应用沙箱内；用户主动保存的常用连接密码放入系统 AssetStore SECRET，不写普通配置、不做云同步，解锁后可用。 |

## 开发顺序和通过条件

先完成源码、原生库与未签名 HAP 的本地构建，再接入手机配置自己的调试签名并安装，按下表完成真机验收。

| 阶段 | 工作与通过条件 |
| --- | --- |
| 1 · 真机和原生构建 | 记录实机型号、系统 API、SDK、Rust 版本及全部源码提交。干净构建 ARM64 原生库和签名 HAP，在真机启动并成功调用一个原生接口；核验证书、ABI、动态依赖和日志。用官方客户端之间的会话先验证测试服务可用。 |
| 2 · 最小远控闭环 | 在同一局域网经 ID 和直连完成认证，看见不断更新的桌面，从手机点开 Windows 记事本、输入文字并断开。再用受控网络限制直连，确认走中继也能完成同一操作。保存脱敏的连接路径、协商编码、双方版本与失败原因。 |
| 3 · 手机交互 | 完成拖动、右键、滚动、中文输入、组合键、缩放和旋转。用窗口四角与中心校准点击位置；旋转、软键盘弹出和显示分辨率变化后复测。只读时仍可查看画面。 |
| 4 · 稳定性和交付 | 测对端拒绝授权、密码错误、公钥错误、对方结束会话、锁屏、断网及 Wi-Fi 切蜂窝。检查退出后无残留连接、卡键或解码线程。交付调试签名 HAP、版本与构建记录、测试结果、已知限制和第三方声明。公开分发另行办理发布签名。 |

**建议的首版性能验收。** 固定一台目标手机、一个 1280×720 的远程显示器和同一 Wi-Fi，记录 RTT 与实际协商的编码。在有连续滚动内容时以平均显示帧率 ≥20 fps 为初始目标；从授权成功到首个可见帧做 10 次测量，目标每次 ≤5 秒。连续控制 30 分钟并重复连接和断开 20 次，检查崩溃、黑屏、内存持续增长及输入滞留。直连和强制中继分开记录；性能目标用于未来验收，目前尚待实测。
